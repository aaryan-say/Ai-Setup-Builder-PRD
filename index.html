§1

Overview

Setup Builder is a new, standalone product — no dependency on, or relation to, any existing screener. It lets a user define a named, reusable screen (a Setup) against a predefined instrument universe, using an arbitrarily nested AND/OR condition tree spanning equity, fundamental, and F&O fields.

Setups run on a schedule. Each run re-evaluates the universe and produces a matched-instrument list surfaced on My Setups, with full per-instrument condition-match transparency and run-over-run diffing. A Setup can optionally bind 1:1 to a watchlist, which is overwritten with the latest matches on every run while remaining fully user-editable in between.

§2

Goals & non-goals

Goals

  • Reusable, named, scheduled screens spanning equity and F&O fields in one condition tree.
  • Arbitrary AND/OR nesting across any condition — including underlying-level conditions applied against a derivative universe.
  • Full transparency: which specific conditions matched, per instrument, per run.
  • Run history sufficient to diff consecutive runs.
  • Optional live 1:1 sync to a watchlist, without removing the user's manual control of it.

Non-goals (v1)

  • Cross-sectional / ranking conditions ("top 10 by relative volume") — explicitly declined; every condition evaluates per-instrument only.
  • Coupling to an existing screener — built from scratch, standalone.
  • Many-to-one watchlist binding — strictly 1:1.
  • Sector-index universes (Nifty Bank, Nifty IT, …) — no constituent list exists via API; only Nifty 50/100/500 are bundled statically.
  • Push / email notifications — in-app only in this spec; delivery ownership sits with the existing notification system.

Glossary

Setup
The saved, named, scheduled screen definition.
Universe
The instrument set a Setup evaluates each run.
Condition
One evaluable rule: field + operator + value or reference.
Condition tree
The arbitrarily nested AND/OR structure grouping conditions.
Run
One scheduled evaluation of a Setup.
Match
An instrument that satisfied the full condition tree in a given run.
My Setups
The page showing each Setup as a card with its latest run's matches.
Watchlist binding
The 1:1 link from a Setup's output to a watchlist, overwritten each run.
§4

User flow

  1. User opens Setup Builder and names the Setup.
  2. User picks a universe type from the fixed catalog (§8). If the type is single-underlying F&O, an instrument search appears to pick the referent (e.g. NIFTY, RELIANCE).
  3. User builds the condition tree: adds conditions, groups them, sets AND/OR per group, nests groups inside groups as needed.
  4. User sets a run schedule (frequency options Deferred — costing).
  5. User optionally binds the Setup's output to a watchlist (strictly 1:1).
  6. On save, and on every scheduled run thereafter: universe resolves → condition tree evaluates → matches persist → My Setups card updates → bound watchlist (if any) is overwritten → user receives an in-app "run complete" notification.
§5

Functional spec

5.1Universe engine Confirmed

  • Universe is chosen from a fixed catalog of types (§8) — never free-form.
  • Single-underlying F&O types require an instrument picked via search at creation time; the type is predefined, only the referent is user-chosen.
  • Derivative universes resolve expiry by relative bucket (near-week / next-week / monthly / far-month), re-resolved to whichever contract currently occupies that slot on every run — never pinned to a fixed date.
  • Option-chain universes default to a strike band around ATM. Exact default width is Open — see §12. "All strikes" is proposed as an explicit opt-in, not yet confirmed.
  • Watchlist- and portfolio-sourced universes resolve to that list's current contents at run start.

5.2Condition & rule engine Confirmed

  • Conditions combine via an arbitrarily nested AND/OR tree — groups may contain groups.
  • A soft UI depth cap is recommended for usability (proposed 4–5 levels); not a functional limit — exact value is Open.
  • Every condition evaluates per-instrument only; no ranking/cross-sectional operators exist anywhere in the engine.
  • When the universe is a derivative universe, conditions may reference the contract's own fields or the underlying's equity/technical fields — both resolve against the same instrument row (see join note, §6).
  • Corporate-action conditions are event/date-window booleans ("did X occur in window Y") — structurally different from the operator+value shape every other condition uses; needs its own leaf shape (§6).

5.3Scheduling & run execution

  • Run frequency options are not yet decided — gated on a cost/infra analysis; some tier-linked limitation is expected. Deferred — costing
  • Every condition carries a pre_open_valid flag. If any condition in a Setup's tree is ineligible for pre-open, the entire run is blocked when scheduled inside the pre-open window — no partial evaluation — and the user is notified why. Confirmed
  • Watchlist-sourced universe inputs are snapshotted at run start; any output write to a bound watchlist happens only at run end — a run never observes its own in-flight writes, even when the same watchlist is both input and output. Confirmed
  • Consequence of the above: a Setup whose universe and output are the same watchlist will, under restrictive AND-heavy conditions, narrow that watchlist run over run — potentially to empty. This is accepted, intended behavior — no auto-reset or reseeding is required. Confirmed

5.4My Setups & diff view Confirmed

  • My Setups renders one card per Setup: name + a matched / total count, where total = universe size as of the latest run.
  • Opening a card shows the current matched list, plus — on this page only, never reflected into a bound watchlist — a run-over-run diff (added since last run / dropped since last run).
  • Diffing is run-over-run only; arbitrary historical comparison across non-adjacent runs is not in scope.
  • Each matched instrument shows exactly which conditions it satisfied — requires persisting match results at instrument × leaf-condition granularity, not just instrument granularity.

5.5Watchlist sync Confirmed

  • A Setup binds to at most one watchlist; a watchlist is bound by at most one Setup — strictly 1:1.
  • The bound watchlist stays fully user-editable between runs; the next run overwrites it again with that run's matches.
  • A watchlist may simultaneously be a Setup's universe input and its output target — ordering guaranteed by §5.3.

5.6Notifications Confirmed

On completion of a scheduled run, the user receives an in-app notification: "Screen run – {Setup name} – completed." Push/email delivery is owned by the existing notification system and out of scope here.

§6

Data model

Five entities cover the spec above. condition_tree is the one recursive structure — everything else is flat.

Setup
  id                    uuid
  user_id               uuid
  name                  string
  status                enum(active, paused, draft)
  universe_type         enum              -- see §8 catalog
  universe_params       jsonb             -- instrument_ref, expiry_bucket, strike_band, watchlist_id...
  condition_tree        jsonb             -- recursive AND/OR node tree, see below
  schedule              jsonb             -- frequency, session window — shape TBD (§12.1)
  watchlist_binding_id  uuid, nullable, fk -> WatchlistBinding
  created_at, updated_at timestamp
ConditionNode  (recursive, lives inside Setup.condition_tree)

  -- group node --
  type        'group'
  bool_op     'AND' | 'OR'
  children    ConditionNode[]

  -- leaf node (operator + value shape — most conditions) --
  type            'leaf'
  field           string            -- e.g. 'rsi_14', 'atm_iv', 'pe_ratio'
  source          'contract' | 'underlying' | 'instrument'
  operator        comparison | range | crossover | pct_change | trend
  value           number | {min,max} | {ref_field, lookback}
  pre_open_valid  boolean

  -- leaf node (event/date-window shape — corporate actions only, §5.2) --
  type            'leaf_event'
  event           'dividend' | 'bonus' | 'split'
  window          {from, to} | {trailing_days}
Run
  id             uuid
  setup_id       fk
  triggered_at   timestamp
  status         'completed' | 'blocked_preopen' | 'failed'
  universe_size  int
  matched_count  int

MatchedInstrument
  run_id             fk
  instrument_id      string
  matched_conditions jsonb[]   -- leaf node id + evaluated value, per condition satisfied

WatchlistBinding
  setup_id      fk, unique
  watchlist_id  fk, unique
  sync_mode     'overwrite_on_run'

Underlying/contract join — when universe_type resolves to a derivative universe, a leaf's source: 'underlying' resolves against the underlying equity row shared by every contract row in that run — same value applied across the whole chain.

§10

Edge cases & failure handling

CaseHandling
Universe empty at run startRun completes as 0/0, still notifies — not an error
Condition field invalid for resolved universe typeRejected at build time by the rule builder — field list must intersect with universe type, not caught at run time
Run blocked pre-openNotification states the reason (ineligible condition present), not just "did not run"
Upstream API failure mid-runRun fails cleanly as status: 'failed', no partial matches persisted — proposed fail-closed default, mirrors the pre-open policy Open
Bound watchlist deleted while Setup activeBinding treated as broken — pause Setup or skip the output-write step Open
§11

Non-functional notes

  • Indicator calls batch ~200 symbols/call — the run scheduler should chunk large universes (e.g. whole exchange) to this, not call per-symbol.
  • Fundamentals support a peers= batch param — same chunking principle.
  • Option-chain universes are the most expensive per run (up to hundreds of contracts per underlying); strike-band bounding (§5.1) is the primary cost lever pending §12.1.
  • Run-history retention is sized by two needs: the diff view (≥2 runs minimum) and whatever audit window product wants — tied to the storage costing pass.
