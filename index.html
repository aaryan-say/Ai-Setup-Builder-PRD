§1

Overview

Setup Builder is a new, standalone product — no dependency on, or relation to, any existing screener. It lets a user define a named, reusable screen (a Setup) against a predefined instrument universe, using a flat set of AND-combined conditions spanning equity, fundamental, and F&O fields.

Setups run on a schedule. Each run re-evaluates the universe and produces a matched-instrument list surfaced on My Setups, alongside a near-miss bucket for instruments that satisfied most, but not all, conditions — with full per-instrument condition transparency and run-over-run diffing. A Setup can optionally bind 1:1 to a watchlist, which is overwritten with the latest full matches on every run while remaining fully user-editable in between. Users can also run an on-demand overlap analysis between any two of their setups' latest matches.

§2

Goals & non-goals

Goals

  • Reusable, named, scheduled screens spanning equity and F&O fields in one flat, AND-combined condition set — including underlying-level conditions applied against a derivative universe.
  • Full transparency: which specific conditions matched — and for near-miss instruments, which were missed — per instrument, per run.
  • A configurable near-miss bucket: instruments that satisfied a user-set percentage of conditions without fully matching, visible only on My Setups.
  • Overlap analysis between any two setups' latest matched lists.
  • Run history sufficient to diff consecutive runs.
  • Optional live 1:1 sync to a watchlist, without removing the user's manual control of it.

Non-goals (v1)

  • OR logic / nested condition groups — v1 evaluates a flat list of conditions, all combined with AND.
  • Corporate-action (event/date-window) conditions — out of scope for this version.
  • Cross-sectional / ranking conditions ("top 10 by relative volume") — explicitly declined; every condition evaluates per-instrument only.
  • Coupling to an existing screener — built from scratch, standalone.
  • Many-to-one watchlist binding — strictly 1:1.
  • Sector-index universes (Nifty Bank, Nifty IT, …) — no constituent list exists via API; only Nifty 50/100/500 are bundled statically.
  • Push / email notifications — in-app only in this spec; delivery ownership sits with the existing notification system.

Glossary

Setup
The saved, named, scheduled screen definition.
Universe
The instrument set a Setup evaluates each run.
Condition
One evaluable rule: field + operator + value or reference.
Condition set
The flat list of a Setup's conditions — all combined with AND, no nesting.
Run
One scheduled evaluation of a Setup.
Match
An instrument that satisfied every condition in a given run.
Near-miss
An instrument that satisfied a user-set % of conditions without fully matching.
Overlap analysis
An on-demand comparison of the latest matches between two setups.
My Setups
The page showing each Setup as a card with its latest run's matches and near-misses.
Watchlist binding
The 1:1 link from a Setup's full matches to a watchlist, overwritten each run.
§4

User flow

  1. User opens Setup Builder and names the Setup.
  2. User picks a universe type from the fixed catalog (§8). If the type is single-underlying F&O, an instrument search appears to pick the referent (e.g. NIFTY, RELIANCE).
  3. User adds conditions as a flat list — every condition is combined with AND; there is no OR or grouping in v1.
  4. User optionally sets a near-miss threshold % (e.g. 70%) — instruments meeting at least that share of conditions, without fully matching, will appear in the near-miss bucket on My Setups.
  5. User sets a run schedule (frequency options Deferred — costing).
  6. User optionally binds the Setup's output to a watchlist (strictly 1:1) — only full matches ever sync; near-miss instruments never do.
  7. On save, and on every scheduled run thereafter: universe resolves → every condition evaluates per instrument → full matches and near-misses persist → My Setups updates → bound watchlist (if any) is overwritten with full matches → user receives an in-app "run complete" notification.
§5

Functional spec

5.1Universe engine Confirmed

  • Universe is chosen from a fixed catalog of types (§8) — never free-form.
  • Single-underlying F&O types require an instrument picked via search at creation time; the type is predefined, only the referent is user-chosen.
  • Derivative universes resolve expiry by relative bucket (near-week / next-week / monthly / far-month), re-resolved to whichever contract currently occupies that slot on every run — never pinned to a fixed date.
  • Option-chain universes default to a strike band of ATM ±5 strikes. "All strikes" is available as an explicit opt-in, never the default — the UI surfaces this default with an info affordance (§14.2) so the user knows it's a system assumption, not something they set. Confirmed
  • Watchlist- and portfolio-sourced universes resolve to that list's current contents at run start.

5.2Condition engine Confirmed

  • Conditions form a flat list, combined with AND only — v1 has no OR logic and no nested groups.
  • Every condition evaluates per-instrument only; no ranking/cross-sectional operators exist anywhere in the engine.
  • When the universe is a derivative universe, conditions may reference the contract's own fields or the underlying's equity/technical fields — both resolve against the same instrument row (see join note, §6).

5.3Scheduling & run execution

  • Run frequency options are not yet decided — gated on a cost/infra analysis; some tier-linked limitation is expected. Deferred — costing
  • Every condition carries a pre_open_valid flag. If any condition in a Setup is ineligible for pre-open, the entire run is blocked when scheduled inside the pre-open window — no partial evaluation — and the user is notified why. Confirmed
  • Watchlist-sourced universe inputs are snapshotted at run start; any output write to a bound watchlist happens only at run end — a run never observes its own in-flight writes, even when the same watchlist is both input and output. Confirmed
  • Consequence of the above: a Setup whose universe and output are the same watchlist will, under restrictive conditions, narrow that watchlist run over run — potentially to empty. This is accepted, intended behavior — no auto-reset or reseeding is required. Confirmed
  • A user can also trigger an on-demand run at any time via "Run now", independent of the schedule. It carries the same evaluation semantics as a scheduled run — full matches, near-miss, and watchlist overwrite all behave identically — and does not reset or otherwise disturb the timing of the next scheduled run. Run.trigger records 'scheduled' | 'manual' (§6). Confirmed

5.4My Setups & diff view Confirmed

  • My Setups renders one card per Setup: name + a matched / total count, where total = universe size as of the latest run.
  • Opening a card shows the current matched list, plus — on this page only, never reflected into a bound watchlist — a run-over-run diff (added since last run / dropped since last run).
  • Diffing is run-over-run only; arbitrary historical comparison across non-adjacent runs is not in scope.
  • Each matched instrument shows exactly which conditions it satisfied — requires persisting results at instrument × condition granularity, not just instrument granularity.
  • The same card also surfaces the near-miss bucket (§5.7) alongside full matches — near-miss instruments show which conditions they satisfied and which they missed.

5.5Watchlist sync Confirmed

  • A Setup binds to at most one watchlist; a watchlist is bound by at most one Setup — strictly 1:1.
  • The bound watchlist stays fully user-editable between runs; the next run overwrites it again with that run's full matches only — near-miss instruments never write to a watchlist.
  • A watchlist may simultaneously be a Setup's universe input and its output target — ordering guaranteed by §5.3.
  • If the bound watchlist is deleted while the Setup is active, the Setup transitions to status: 'paused' with paused_reason: 'watchlist_deleted' (§6) — it does not keep running with the write silently skipped. The user sees "bound watchlist no longer exists — re-bind or remove the sync" and must act before the Setup resumes. Confirmed

5.6Notifications Confirmed

On completion of a scheduled run, the user receives an in-app notification: "Screen run – {Setup name} – completed." Push/email delivery is owned by the existing notification system and out of scope here.

5.7Near-miss criteria Confirmed mechanic

  • Each Setup carries an optional, user-set near_miss_threshold_pct (§4) — e.g. 70%.
  • On every run, every universe instrument is evaluated against all conditions (not short-circuited on the first false) to compute match_pct = (conditions satisfied ÷ total conditions) × 100.
  • match_pct = 100 → full match — existing behavior, eligible to sync to a bound watchlist.
  • threshold ≤ match_pct < 100 → near-miss — shown only on My Setups.
  • match_pct < threshold → not surfaced at all.
  • The threshold is an optional toggle, off by default. When a user turns it on, it defaults to 70% — surfaced with an info affordance (§14.2) so the default reads as a system assumption, not a requirement. Confirmed

5.8Overlap analysis Confirmed

  • From My Setups, a user picks exactly two of their own setups and views the overlap between their latest results. N-way (3+) comparison is an explicit v2 candidate, not silently dropped — it needs a genuinely different visualization (a matrix/upset plot, not simple cards) and wasn't worth blocking v1 on. Confirmed
  • Computed on demand from each Setup's latest run — not scheduled, and not persisted as its own entity.
  • The comparison includes both full matches and near-miss instruments, not full matches only. Confirmed
  • If one of the two setups has near-miss disabled (or a different threshold set), that setup simply contributes an empty near-miss set to the comparison — the overlap still computes on whatever's available rather than blocking or erroring. Confirmed
  • Output renders three groups: Only in A, In both (the intersection), and Only in B — the exclusive breakdowns ship alongside the intersection, not just the intersection alone. Confirmed

Data model

Five entities cover the spec above. Setup.conditions is a flat array — no recursive tree in v1.

Setup
  id                       uuid
  user_id                  uuid
  name                     string
  status                   enum(active, paused, draft)
  paused_reason            string, nullable  -- e.g. 'watchlist_deleted'; shown in UI when status='paused'
  universe_type            enum              -- see §8 catalog
  universe_params          jsonb             -- instrument_ref, expiry_bucket, strike_band (default ±5), watchlist_id...
  conditions               ConditionNode[]   -- flat list, all ANDed — see below
  near_miss_threshold_pct  number, nullable  -- null = off (default); enabled default is 70
  schedule                 jsonb             -- frequency, session window — shape TBD (§12.1)
  watchlist_binding_id     uuid, nullable, fk -> WatchlistBinding
  created_at, updated_at   timestamp
ConditionNode  (flat leaf — no group/nesting type in v1)

  id              string
  field           string            -- e.g. 'rsi_14', 'atm_iv', 'pe_ratio'
  source          'contract' | 'underlying' | 'instrument'
  operator        comparison | range | crossover | pct_change | trend
  value           number | {min,max} | {ref_field, lookback}
  pre_open_valid  boolean            -- defaults false until the field is audited (§12.5)
Run
  id              uuid
  setup_id        fk
  trigger          'scheduled' | 'manual'  -- 'manual' = user-initiated "Run now" (§5.3)
  triggered_at    timestamp
  status          'completed' | 'blocked_preopen' | 'failed'
  universe_size   int
  matched_count   int
  near_miss_count int

RunResult  (renamed from MatchedInstrument — now covers matches and near-misses)
  run_id              fk
  instrument_id       string
  status              'matched' | 'near_miss'
  match_pct           number   -- conditions satisfied ÷ total conditions × 100
  matched_conditions  jsonb[]  -- condition id + evaluated value, per condition satisfied
  missed_conditions   jsonb[]  -- condition id + evaluated value, per condition NOT satisfied (near_miss only)

WatchlistBinding
  setup_id      fk, unique
  watchlist_id  fk, unique
  sync_mode     'overwrite_on_run'  -- writes RunResult rows with status:'matched' only

Underlying/contract join — when universe_type resolves to a derivative universe, a leaf's source: 'underlying' resolves against the underlying equity row shared by every contract row in that run — same value applied across the whole chain.

§11

Non-functional notes

  • Indicator calls batch ~200 symbols/call — the run scheduler should chunk large universes to this, not call per-symbol. With whole-exchange removed (§8), Nifty 500 (3 chunks) is now the largest equity universe rather than ~2,143 names (11 chunks) — a meaningful reduction in the v1 cost ceiling.
  • Fundamentals support a peers= batch param — same chunking principle.
  • Option-chain universes are the most expensive per run (up to hundreds of contracts per underlying); strike-band bounding at the confirmed ±5-strike default (§5.1) is the primary cost lever.
  • Near-miss (§5.7) requires evaluating every condition for every instrument in the universe — no short-circuiting on the first false — to compute match_pct. This is strictly more compute than match-only evaluation; factor it into the §12.1 costing pass.
  • On-demand "Run now" (§5.3) adds unscheduled, unpredictable load spikes on top of the regular schedule — factor this into the §12.1 costing pass alongside frequency and tier limits.
  • Run-history retention is sized by two needs: the diff view (≥2 runs minimum — now a confirmed floor, §12.4) and whatever audit window product wants for the final retention window — tied to the storage costing pass.

§14

Frontend requirements

Setup Builder had no written frontend spec before v1.2 — UI behavior only existed implicitly in the simulation (§15). This section formalizes it. Screens and components below map directly onto that prototype; where this section and the simulation ever disagree, this section is authoritative and the simulation should be updated to match.

14.1Cross-cutting UI principles Confirmed

No black-box "draft from a sentence." Setup creation must never be a single-step "describe it in English → AI drafts the setup" action. Any AI-assisted entry point (e.g. a natural-language prompt suggesting condition ideas) must resolve into the same explicit, editable condition rows as manual creation, and the user reviews and confirms the exact rules before save. The value of a Setup is that it's a deterministic, auditable rule set — if "oversold" silently becomes some hidden RSI threshold the user never sees, near-miss %, overlap analysis, and trust in the matches all break down.

Every system-picked default gets an i-button. Wherever the UI shows a value the system assumed rather than the user explicitly set — the ±5 strike-band default, the 70% near-miss default, any other default introduced later — an i info affordance sits right next to it, not buried in a help doc. Click/hover reveals what the assumption is and why.

14.2My Setups (dashboard) Confirmed

  • One card per Setup: name, matched / total count, near-miss count if the threshold is enabled.
  • Per-card actions: Open (detail view), Edit (re-enter the builder), Run now (§5.3, §12.9) — triggers an on-demand run without disturbing the schedule.
  • A Setup with status: 'paused' shows its paused_reason directly on the card (e.g. "Paused — bound watchlist no longer exists"), not just in the detail view.
  • Empty state: first-run "no setups yet" prompt into the builder.

14.3Setup Builder (creation wizard) Confirmed

  • Five steps: Name & universe → Conditions → Near-miss → Schedule → Output, matching §4's user flow.
  • Universe step: fixed-catalog picker (§8, now without whole-exchange) — never a free-text universe field. Single-underlying F&O types reveal an instrument search.
  • Conditions step: a searchable condition library (§7, 180+ fields) filtered to what's valid for the chosen universe type; added conditions render as a flat, removable list — no grouping/nesting UI, matching §5.2.
  • Conditions step also computes and shows: which added conditions are/aren't pre-open valid (§12.5), and a live "N of N conditions, all valid for this universe" check before the user can proceed.
  • Near-miss step: an optional toggle (default off); enabling it reveals a threshold slider defaulting to 70%, with the i-button from §14.1 and a live "≥ N of M conditions must be true" readout.
  • Schedule step: frequency picker (options pending §12.1) and the pre-open-block warning when any condition isn't pre-open valid.
  • Output step: optional 1:1 watchlist binding, with the self-narrowing-watchlist warning (§5.3) shown when the bound watchlist is also the universe source.
  • Review/save: a live checks panel (name set, ≥1 condition, pre-open validity, watchlist binding state) must all pass before "Save" is enabled; "Save as draft" is always available regardless of check state.

14.4Setup detail Confirmed

  • Tabs: Matches, Near-miss (only if threshold enabled), Run history.
  • Matches tab: latest full-match list plus the run-over-run diff (added/dropped since the previous run only, §5.4) and per-instrument condition transparency.
  • Near-miss tab: per-instrument match_pct and which specific conditions were missed.
  • Run history tab: list of runs with status (completed/blocked_preopen/failed), trigger (scheduled/manual), matched and near-miss counts.
  • A paused Setup shows a persistent banner with its paused_reason and the action needed to resume (re-bind or remove the watchlist sync).

14.5Overlap analysis Confirmed

  • Two-setup picker (§5.8, §12.13) — no N-way selection UI in v1.
  • Three result groups: Only in A, In both, Only in B (§12.12), computed across full matches and near-miss (§12.11).
  • If either selected setup has near-miss disabled, the UI notes that its near-miss contribution is empty rather than presenting a silently incomplete comparison.
  • Zero-state (disjoint universes, §10) renders as a legitimate zero intersection, not an error.
